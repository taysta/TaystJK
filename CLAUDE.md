# CLAUDE.md

Behavioral guidelines to reduce common LLM coding mistakes. Merge with project-specific instructions as needed.

**Tradeoff:** These guidelines bias toward caution over speed. For trivial tasks, use judgment.

## 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:

- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

## 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

## 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:

- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:

- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

## 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:

- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:

```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

---

**These guidelines are working if:** fewer unnecessary changes in diffs, fewer rewrites due to overcomplication, and clarifying questions come before implementation rather than after mistakes.

## Repository shape: two branches

This is the **documentation site** for TaystJK, a cross-platform Jedi Academy multiplayer
client. Work spans two branches of one repository:

- **`gh-pages`** (and `gh-pages`-family branches like the current one) — the Jekyll site.
  Served at https://taysta.github.io/TaystJK/ with `baseurl: /TaystJK`. This is where you edit.
- **`master`** — the C/C++ game engine source. The reference pipeline reads registrations
  from here; the docs branch never contains the engine.

Most tasks read `master` while writing `gh-pages`. A worktree is checked out so both are
readable at once:

    /Users/tayst/CLionProjects/TaystJK        <- docs branch (gh-pages family)
    /Users/tayst/CLionProjects/TaystJK-src    <- master (engine source)

Recreate it if missing: `git worktree add ../TaystJK-src master`.

Untracked `build/`, `cmake-build-*/`, `lib/`, `compile_commands.json`, `.idea/` are local
artifacts, not part of the site.

## Site engine

- Jekyll with **no theme**. Every layout is local: `_layouts/reference.html` is applied to
  every page by `defaults`, and `_layouts/none.html` is raw output for the redirect stubs
  and `search-index.json`. Navigation is hardcoded in `reference.html` — adding a page to
  the top nav means editing that file. `nav_order` and `parent` front matter are inert
  leftovers; `nav_exclude` survives only because the layout reuses it for the reference
  breadcrumb.
- The site is built by GitHub Pages. There is **no `Gemfile` and no local Jekyll install**
  here, so `bundle exec jekyll serve` does not work out of the box. Use
  `tools/cvar_audit/check_generated.py` as the local validation proxy for the generated
  pages and internal links.
- Site JS: `assets/js/reference-app.js` (the console reference's filtering UI **and** the
  platform selector) and `assets/js/site-search.js` (heading anchors and the header search).
  Site CSS: the single hand-written `assets/css/reference.css`; there is no Sass.
- Site-wide search reads `/search-index.json`, which Liquid generates at build time from
  `site.pages`. Pages opt out with `search_exclude`.

## The reference pipeline (`tools/cvar_audit/`)

Statically extracts every cvar/command registration from the engine source, resolves which
upstream project each originated from, and generates the reference. See
`tools/cvar_audit/README.md` for the full contract. Scripts:

- `extract.py` — dependency-free C/C++ parser; pulls cvar/command registrations from a git
  ref, preserving line numbers and conditional registrations (tolerant of X-macros).
- `provenance.py` — resolves origin/attribution across the upstream graph from exact git
  history and explicit credits. Caches under `.cvar-audit/cache`; `--limit 0` prewarms,
  `--refresh` after upstream refs move.
- `build_reference.py` — assembles the evidence-backed `_data/*.json` from the
  extraction/provenance caches.
- `runtime_check.py` — reconciles `_data` against live `+cvarlist` / `+cmdlist` capture
  (supplements, never replaces, static extraction).
- `generate_docs.py` — renders the Markdown reference pages and `assets/data/catalog.json`
  from `_data/*.json`.
- `validate.py` — validates checked-in `_data` records against `schema.json`.
- `check_generated.py` — validates generated pages and internal `/TaystJK/` links; imports
  `generate_docs.py`, so regenerate before running it after generator changes.
- `check_drift.py --ref <ref>` — fails when source registrations at `<ref>` diverge from
  checked-in `_data`.
- Data: `schema.json` (record schema), `overrides.json` (manual field overrides),
  `removed.json` (intentionally dropped entries).

Regenerate (from repo root), in order:

    python3 tools/cvar_audit/provenance.py --pr-json <page-1.json> --pr-json <page-2.json>
    python3 tools/cvar_audit/build_reference.py
    python3 tools/cvar_audit/runtime_check.py --cvars <cvarlist.txt> --commands <cmdlist.txt> --build <BUILD_ID>
    python3 tools/cvar_audit/generate_docs.py

`provenance.py` expects local remote-tracking refs for every origin project: `origin/master`,
`openjk/master`, `eternaljk/master`, `japro/main`, `jk2mv/master`, `newjk/master`,
`somaz/rend2-unified-wip`, `Sunny/master`.

## Verification

Run all eight after any pipeline or generated-content change (this is what CI runs):

    python3 tools/cvar_audit/test_extract.py
    python3 tools/cvar_audit/test_provenance.py
    node    tools/cvar_audit/test_reference_app.js
    node    tools/cvar_audit/test_site_search.js
    python3 tools/cvar_audit/test_liquid.py
    python3 tools/cvar_audit/validate.py
    python3 tools/cvar_audit/check_generated.py
    python3 tools/cvar_audit/check_drift.py --ref origin/master

CI: `.github/workflows/reference-drift.yml` runs the same set, but only on `gh-pages`
push/PR and `workflow_dispatch` — never on `master`. Note `origin/master` currently equals
the pinned `source_commit`, so `check_drift` against it only catches drift once origin
advances; point `--ref` at the true source tip to test real drift.

## Front-matter fields in use (hand-written pages)

- `title` — quoted string (Unicode-escaped em dashes appear, e.g. `—`).
- `layout: reference` — set explicitly on every page (the default also supplies it).
- `description` — one sentence; drives listing cards and meta tags. Present on every page.
- `nav_order` — integer; top-level order is index 1, install 2, hosting 3, development 4,
  reference 5.
- `wide: true` — opt-in wider content column (index, development, reference).
- `reference_app: true` — only on `reference.md`; mounts the search app.
- `parent`, `nav_exclude` — used by legacy/child pages.
- Legacy orphans additionally use `has_children` and `permalink` (anchor targets).

## Prose conventions (from install.md and server-hosting.md)

- Page opens with a heading block:
  `<div class="page-heading" markdown="1">` containing
  `<p class="eyebrow">…</p>` (a role label, e.g. "Player guide", "Administrator guide"),
  then the `#` H1, then `<p class="page-lede">…</p>` for the intro sentence.
- Direct, second-person, imperative instructions ("You need…", "Choose your operating
  system…", "Start with a small, private server"). No marketing tone.
- Source links are GitHub **blame** links pinned to a commit hash (currently the
  `source_commit` `6ff04c0…`), e.g. `.../blame/6ff04c0…/docker-compose.yml`.
- Code fences carry a language tag (`text`, `sh`).
- The platform selector uses an ARIA `role="tablist"` pattern with per-device saved
  selection; reuse that markup for any new toggle rather than inventing one.
